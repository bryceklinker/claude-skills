# Testing and Verifying Infrastructure — the TDD/verification split, made concrete

Infrastructure-as-code is two different kinds of thing wearing one file extension: logic (policy decisions, computed values, generated names, anything with a branch or a calculation in it) that happens to live alongside declarative resource definitions, and the declarative resources themselves — the resource blocks and their wiring, whose entire behavior is what they cause a cloud provider to actually do. Those two kinds of thing are proven correct by two different methods, and conflating them is how infrastructure ends up either untested (because "you can't unit test a resource block") or under-verified (because someone read the plan, thought it looked fine, and applied it without ever watching the resource actually converge). This document makes the split from the skill's `SKILL.md` concrete: what actually goes through `strict-tdd`, what actually goes through `verification`, and the minimum verification that must happen even when a full apply isn't possible.

## What counts as logic: unit-test it under strict-tdd

**Policy-as-code checks, modules that compute a value rather than just passing one through, name/tag generators, and any scripting the IaC calls out to are production code, and they go through `strict-tdd` exactly like application code: a failing test first, then the minimal code to pass it.**

Each of these has real branching logic with real edge cases — a policy that rejects a change past a certain risk threshold, a module that derives a subnet CIDR from an index and a base range, a generator that builds a resource name from environment and service and has to handle the case where the combination is too long for the provider's limit. Every one of those edge cases (boundary values, malformed input, the empty or maximal case) is something a unit test pins down in milliseconds, run locally, with no cloud account and no apply required. Treating this code as "just config because it lives near a `.tf` file" throws away the fastest, cheapest feedback loop available and defers every one of those edge cases to whatever happens to show up in a plan someone reads once.

## What counts as declarative: verify it, don't unit-test it

**The resource blocks themselves — what gets created, with what arguments, wired to what — are not unit-testable in any meaningful sense, and trying to force them into that mold produces tests that mock the cloud provider rather than exercise it.** This half is proven by `verification`: run the real tooling against the real definition and observe what it actually does.

The reason a unit test is the wrong tool here is the same reason it's wrong for pipeline glue: a resource block has no interesting internal logic to isolate — its entire behavior *is* its integration with the provider's API, and a provider is exactly the kind of external, stateful, non-deterministic system `strict-tdd` doesn't reach into. A test that mocks the provider to make the resource "testable" verifies only that the code calls the mock the way the test author expected — a tautology that would pass even if the real definition were subtly broken, missing a required argument, or pointed at the wrong region. What actually needs answering — "does this apply create what I think it creates," "does the computed value from the module actually land in the right argument," "does removing this block really destroy only what I intend" — can only be answered by running the real tooling.

## `validate` + `plan` is the always-runnable minimum verification

**Running `validate` and then `plan`/`diff` catches broken references, type errors, and unexpected destroy/replace entirely offline, before any apply is attempted — and the plan is a diff that must be READ, not a step that gets rubber-stamped because the command exited zero. This is the infrastructure analog of smoke-invoking a script through its real entrypoint: it doesn't prove the logic is correct, but it proves the seam between the definition and the provider's understanding of it is actually connected.**

A definition can be internally self-consistent and still be wrong in ways only the provider's own type-checking and dependency graph will catch — a reference to an attribute a resource doesn't expose, a required argument left unset, a circular dependency between two modules. `validate` catches the class of error that never depends on cloud state at all; `plan` goes further and shows exactly what would change against the real or last-known state, without changing anything. Because both run without touching live infrastructure, there's no excuse for skipping them — no sandbox account, no budget, no access needed, just the tool and the source. And because the plan is a diff, reading it is not optional: a plan that proposes destroying and recreating a resource nobody meant to touch is exactly as visible in that diff as it would be in a code review, but only to someone who actually reads it rather than checking that the command completed.

## Apply against a throwaway or sandbox environment and observe convergence

**Once the plan has been read and looks right, verify the apply itself by running it against a throwaway or sandbox environment — a scratch workspace, a disposable account, a non-production target — and observing the real outcome: did the resources that were supposed to be created exist afterward, with the arguments the definition specified, and does a second `plan` immediately after show no further changes.** This is evidence, not inspection — reading the definition and reasoning that it "looks right" is exactly the failure mode verification exists to rule out, the same way reading application code without running its tests would be.

Concretely: apply for real, against infrastructure close enough to production's shape that the outcome is trustworthy, targeting an environment that can be safely torn down or reset afterward. Capture what actually happened — the apply's output, the resulting resource attributes, the follow-up plan showing convergence — as the record that verification occurred, not a description of what should have happened. A module that's never been applied anywhere is a module whose correctness is still just an assumption, no matter how carefully the `plan` output was read.

## Review before apply: the gate whose first job is catching a durable resource on its way out

**Every plan is reviewed by a human or a reviewing agent before the corresponding apply runs — no exceptions for changes that look small or "obviously safe." The very first thing that review is checking for is a durable resource marked for destroy or replace, and a durable resource that's ended up inside a compute unit's lifecycle (see `iac-authoring-hygiene.md`) will show up in exactly that form: the compute unit's routine replacement dragging the durable resource down with it in the same diff.**

This gate exists because `validate` and `plan` prove the definition is internally consistent and show what would happen — they don't stop anything from happening. Only review sits between "the plan is computed" and "the plan is executed," which makes it the last point where a destroy/replace on something irreplaceable can be caught before it's too late to matter. A destroy/replace on a stateless compute unit is background noise, expected on nearly every deploy; a destroy/replace on a database, object store, queue, or bus in the same plan is the single line a reviewer has to catch every single time, because there is no lifecycle guard or `validate` check that substitutes for a human looking at the plan and asking "is this resource supposed to be destroyed." Treating review as a formality for changes that "obviously" don't touch anything durable is how the one change that does touch something durable slips through unnoticed.

## Shrinking the surface only verification can cover

**The amount of infrastructure that only `plan`-reading and sandbox applies can prove correct is not fixed — it's a direct consequence of how aggressively logic gets pushed out of the declarative resources and into tested modules, generators, and policy checks per `iac-authoring-hygiene.md`. The more of the actual decision-making lives in something `strict-tdd` can reach, the less of the definition is doing anything beyond "declare this resource with these already-validated inputs."**

A definition where every computed value, every conditional, and every generated name is inlined directly into resource arguments has almost nothing strict-tdd can reach — nearly all of it has to be proven by reading every plan and applying to a sandbox, every time, for every change, no matter how small. A definition where that logic has been extracted into tested modules and generators inverts that ratio: most of the actual decision-making is covered fast, locally, and precisely by unit tests, and verification is left with a genuinely smaller job — confirming the wiring between already-trusted, already-tested pieces converges the way the plan said it would — instead of standing in for all the testing the definition never got.
