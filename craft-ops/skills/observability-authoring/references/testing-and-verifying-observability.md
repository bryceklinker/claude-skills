# Testing and Verifying Observability — the TDD/verification split, made concrete

Observability-as-code is two different kinds of thing wearing one repository: logic (SLO and burn-rate computation, instrumentation helpers, alert-expression generators, runtime-lever toggling) that happens to live in scripts or modules the dashboards and alerts call, and the declarative config itself — the dashboard panels, the alert-rule definitions, the datasource wiring — whose entire behavior is what it causes a monitoring system to actually query, render, and page on. Those two kinds of thing are proven correct by two different methods, and conflating them is how observability ends up either untested (because "you can't unit test a Grafana panel") or falsely trusted (because someone read the alert expression, judged it correct, and never once watched it actually fire). This document makes the split from the skill's `SKILL.md` concrete: what actually goes through `strict-tdd`, what actually goes through `verification`, the always-runnable minimum, and why a correct-looking alert expression proves nothing about whether the alert works. Tools referenced below — OpenTelemetry, Grafana, Prometheus, Alertmanager — are examples; the rules apply to whatever stack is in play.

## What counts as logic: unit-test it under strict-tdd

**Metric/SLO/burn-rate computation, instrumentation helpers, alert-expression generators, and runtime-lever toggle logic — anything extracted per `observability-as-code-hygiene.md` — is production code, and it goes through `strict-tdd` exactly like application code: a failing test first, then the minimal code to pass it.**

This follows directly from extraction: the entire reason burn-rate math and lever-toggle logic get pulled into a shared, tested module instead of living inline in a dashboard query or a flag default is so they *can* be given independent test coverage. A burn-rate calculation has real edge cases — a window with zero requests, a metric that's missing a data point, a rate that flaps exactly at the SLO boundary within the same evaluation window — and each of those is something a unit test pins down in milliseconds, with no live signal, no monitoring backend, and no incident required. An instrumentation helper that decides which fields get attached to a span, or a generator that renders an alert expression from a threshold and a window, has the same shape: real branching logic that deserves the fastest feedback loop available rather than being deferred to whatever the dashboard happens to render the day someone looks at it.

## What counts as declarative: verify it, don't unit-test it

**The dashboard definition and the alert-rule config themselves — the panels, the queries, which alert is wired to which notification channel — are not unit-testable in any meaningful sense, and trying to force them into that mold produces tests that mock the monitoring backend rather than exercise it.** This half is proven by `verification`: run the query or fire the alert against a real or synthetic signal and observe what actually happens.

The reason a unit test is the wrong tool here is the same reason it's wrong for IaC resource blocks and rollout manifests: the dashboard or alert config has no interesting internal logic to isolate — its entire behavior *is* its integration with the metrics store, the query engine, the alerting backend. A test that mocks the monitoring system to make the config "testable" verifies only that the config calls the mock the way the test author expected — a tautology that would pass even if the real dashboard pointed a panel at the wrong metric, or the real alert rule referenced a label that doesn't exist. What actually needs answering — "does this query resolve to real data," "does this alert trip when the signal is bad," "does it stay quiet when the signal is healthy" — can only be answered by running the real thing.

## Validate + entrypoint-smoke-invoke is the always-runnable minimum

**Two checks run offline, before any live signal is involved, and there's no excuse for skipping either: validate/lint the alert rules and dashboard definitions against the monitoring backend's schema, and smoke-invoke each extracted script through the exact entrypoint it's called by — `./generate-alerts.sh --dry-run`, `python -m observability.render_dashboard --check` — plus a tool-level validate where the backend supports one (`promtool check rules`, `amtool config check`).**

A script's unit tests import its functions directly; the dashboard-generation pipeline or the deploy step invokes it through a CLI entrypoint or console command. Those are two different call paths, and unit tests exercise only the first. A wrong module path, a renamed script, a malformed alert-rule YAML, a dashboard query referencing a metric that was renamed — none of it shows up in a green unit suite, and all of it fails the moment something tries to load the config for real, usually discovered mid-incident when the dashboard someone needs won't render or the alert that should have paged never loaded. Validating/linting the rule and dashboard definitions catches the class of error that never depends on a live signal at all — a malformed field, a query referencing an undefined datasource, a rule with invalid PromQL. Smoke-invoking each script through its real entrypoint proves the seam between the tested logic and the way it's actually invoked is connected — not a re-test of the burn-rate math itself, but confirmation that the CLI or module path the pipeline calls is exactly the one that exists. Because both run without a live signal, a monitoring backend under real load, or any traffic, they're the minimum verification that must happen even when nothing else can — the observability equivalent of `validate` + `plan` for IaC, or entrypoint-smoke-invocation for rollout scripts.

## Prove the alert fires: exercise it against a real signal

**An alert is not verified — no matter how correct its expression reads — until it has actually been fired against a synthetic or replayed signal that should trip it, and observed to trip. It is then confirmed to stay quiet against a healthy signal, so it's known to distinguish the two, not just react to anything.**

This is the observability-specific case where "verify, don't inspect" carries the most weight, because an alert is exactly the mechanism that only matters during the one moment it's needed — an incident — and reading its expression is not the same as knowing it fires. An alert expression can look completely correct — the right metric, the right operator, a threshold that matches the SLO — and still never fire in practice, because the label it filters on doesn't match what the metric actually emits, because the evaluation window is shorter than the interval data arrives on, because the query silently returns no series instead of a zero. None of that is visible from reading the rule; all of it is visible the instant the rule is actually evaluated against a signal engineered to cross the threshold. Firing it for real — replaying a recorded bad signal, injecting a synthetic one, or driving the underlying metric past the threshold in a test environment — and watching the alert actually transition to firing is the only thing that proves the wiring end to end. Confirming it then stays quiet against a healthy signal closes the other half: an alert that fires on everything is exactly as useless as one that never fires, just louder about it. The failure mode this rule exists to prevent is discovering, during the real incident, that the page everyone was counting on never came — and finding out only then that "the expression looked right" was never actually evidence that it worked.

## Shrinking the surface only verification can cover

**The amount of observability-as-code that only config-reading and live-signal runs can prove correct is not fixed — it's a direct consequence of how aggressively metric, burn-rate, and alert-generation logic gets pushed out of the declarative dashboard/alert config and into tested modules per `observability-as-code-hygiene.md`. The more of the actual computation lives in something `strict-tdd` can reach, the less of the observability layer is doing anything beyond "wire this already-tested value into this panel or rule."**

A dashboard and alert set where every threshold and every burn-rate formula is written directly into the query language has almost nothing strict-tdd can reach — nearly all of it, including every edge case, has to be proven by firing signals at it end to end, every time, for every change. A set where that logic has been extracted into tested modules inverts the ratio: the edge cases are covered fast and locally by unit tests, and verification is left with a genuinely smaller job — confirming the wiring between already-trusted values and the dashboard/alert config renders and trips the way it's supposed to, and that the alert still fires on a bad signal — instead of standing in for all the testing the underlying computation never got.
