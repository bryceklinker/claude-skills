# Observability-as-Code Hygiene — instrumentation that stays true to what it measures

A dashboard clicked together by hand and an alert threshold copy-pasted from another environment both look like observability right up until the moment they're needed — and then they're either stale, wrong, or silent, because nothing ever forced them to stay in sync with the system they claim to describe. Hygiene here isn't cosmetic — it's the set of structural habits that keep dashboards, alerts, and instrumentation reviewable, reproducible, and honest about what they actually observe, instead of artifacts that only look trustworthy until the first incident asks something of them. This document makes the domain rules from the skill's `SKILL.md` concrete, each with the failure it exists to prevent. Tools referenced below — OpenTelemetry, Grafana, Prometheus, Alertmanager — are examples; the rules apply to whatever stack is in play.

## Prefer generated/extracted over hand-maintained duplication

**Dashboards and alert rules are version-controlled code — authored as templates, generators, or declarative definitions that are reviewed like any other change — never built by clicking through a UI and never copy-pasted between environments. Instrumentation calls go through a shared, tested helper, not ad hoc calls re-typed at every call site.**

Click-ops dashboards live entirely in one operator's browser session: nothing forces the panel someone built for staging to match what gets built for production, nothing captures *why* a query is shaped the way it is, and nothing stops the next person from clicking a slightly different version next to it. Copy-paste is the same failure with a paper trail — the alert threshold gets duplicated into a new environment, the underlying service changes, and one copy silently drifts from reality while looking identical to the other. A dashboard or alert defined as code gets a diff a reviewer can actually read, a history that shows when and why a threshold changed, and a single source that every environment renders from — so drift becomes a merge conflict instead of a silent divergence nobody notices until the alert that should have fired doesn't. Instrumentation calls scattered ad hoc across the codebase have the identical problem at the call-site level: one team's `span.start()` tags a field the others don't, a naming convention drifts service by service, and nothing catches it because there's no shared thing to test. Routing every instrumentation call through one shared, tested helper makes the shape of what gets emitted a property of the helper's test suite, not a hope that every call site remembered to do it the same way. This is the rule everything else in this document assumes, because it's the one that determines whether the observability layer is something the team actually trusts or something that merely looks present.

## Wire the runtime levers for real

**The verbosity, sampling, and trace-detail levers the design note decided on are wired to actual runtime configuration or feature flags — not baked in as constants at build time — with a default setting and a distinct incident setting, cost/cardinality guardrails on the incident setting, and an auto-revert so elevated detail doesn't stay on indefinitely.**

An observability design earns nothing if the levers it specified can only be changed by shipping a new build. The entire point of deciding "sample at 1% normally, 100% during an incident" or "log at info by default, debug when investigating" is that the detail level needs to move *faster than a deploy* — during the ten minutes an incident is actually unfolding, not after the fix for the next one ships. Wiring the lever to real runtime config is what makes that possible: flip a flag, and the system emits more without a rebuild, a restart, or a wait. But a lever that's easy to raise and has no guardrail or auto-revert is its own hazard — full-detail tracing or debug logging left on after the incident closes quietly inflates ingestion cost and cardinality until someone notices the bill, and by then it's been running that way for days. The incident setting needs its own explicit cost/cardinality ceiling, and the elevation needs to expire on its own — a TTL, a scheduled revert, an explicit "turn this back down" step wired into the incident-close process — so the detail ramps up when it's needed and back down without depending on someone remembering to undo it by hand.

## Alert on symptoms, not causes

**Alerts page on what the user or the SLO actually experiences — elevated error rate, degraded latency, saturation — not on every internal condition that might, or might not, be contributing to it.**

An internal cause and user-visible pain are not the same event, and treating them as interchangeable is how an on-call rotation gets trained to ignore its own pager. A queue depth spike, a retrying dependency, a single pod restarting — these are causes that may resolve themselves, may be absorbed by redundancy, or may never actually degrade what a user experiences. Paging on every one of them means most pages arrive for conditions nobody needs to act on right now, and the predictable outcome is that people stop treating a page as urgent — which is exactly the moment a page that *does* represent real user pain gets the same shrug as the noise around it. Alerting on the symptom instead — the SLO burning down, the error rate a user would actually notice — means every page that fires represents something worth waking up for, and the causes underneath it become something to investigate *during* that page rather than a reason to page on their own.

## Cardinality guardrails

**Every label or dimension attached to a metric has a bounded, enumerable set of possible values, decided and reviewed at authoring time — never a raw user ID, a full request path, a session token, or any other dimension whose value space is effectively unbounded.**

A metrics store's cost and query performance are both direct functions of how many distinct label combinations exist — its cardinality. A label like `http.status_code` or `region` has a handful of possible values and stays cheap forever; a label like `user_id` or the raw, un-templated request path has as many possible values as there are users or requests, and every new one is a new time series the store has to allocate, index, and retain. That growth is invisible in normal development, where the local dataset is small enough that nothing looks wrong, and then catastrophic in production, where it shows up as a metrics bill that quietly multiplies or a store that falls over under its own index size — usually discovered only once someone is trying to use it during an incident and it's too slow or too expensive to query. Bounding the label set at authoring time — templating a path instead of using it raw, hashing or bucketing an otherwise-unbounded field, pushing anything genuinely high-cardinality into logs or traces instead of metric labels — is what keeps the metrics layer affordable and fast for the entire lifetime of the system, not just the day it launched.

## No secrets in dashboard/datasource/alert config

**Dashboard definitions, datasource configuration, and alert-rule/notification config reference credentials by indirection — a secret-store path, an injected environment variable, a reference resolved at deploy time — never a plaintext API key, webhook URL with an embedded token, or connection string authored directly into any of it.**

Observability config is reviewed, diffed, and stored the same way the rest of the codebase is — committed to a repo, visible to everyone with read access, cached in every clone, and permanent in history even after a later commit tries to remove it. A datasource definition with a plaintext database credential, or an alert's notification channel with a webhook URL that embeds a bearer token, leaks that credential to the same audience as the code itself the moment it's committed — and unlike an application secret, an observability-config secret is easy to overlook precisely because the file doesn't look like it holds credentials at a glance. Injection at deploy time keeps a secret's exposure scoped to the system that actually needs it and makes rotation a matter of updating the secret store rather than a config change that has to be re-reviewed and re-deployed everywhere it was copied. This is the same failure mode "no secrets in the pipeline" and "no secrets in IaC" both guard against, applied to the layer that's watching everything else — a leaked credential here has direct read or write access to whatever telemetry system it authenticates to.
