# Testing and Verifying Rollouts — the TDD/verification split, made concrete

A rollout definition is two different kinds of thing wearing one file extension: logic (gate evaluation, promotion/halt decisions, flag-targeting rules) that happens to live in a script the rollout calls, and the declarative rollout config itself — the canary/blue-green resource and its wiring, whose entire behavior is what it causes a progressive-delivery controller to actually do. Those two kinds of thing are proven correct by two different methods, and conflating them is how rollouts end up either untested (because "you can't unit test a canary step") or falsely trusted (because someone read the manifest, watched the forward path go green once, and assumed the rollback attached to it would work too). This document makes the split from the skill's `SKILL.md` concrete: what actually goes through `strict-tdd`, what actually goes through `verification`, the always-runnable minimum, and why a green forward path proves nothing about rollback.

## What counts as logic: unit-test it under strict-tdd

**Health-gate evaluation, promotion/halt decisions, flag-targeting logic, and any generator or script the rollout calls — anything extracted per `rollout-authoring-hygiene.md` — is production code, and it goes through `strict-tdd` exactly like application code: a failing test first, then the minimal code to pass it.**

This follows directly from extraction: the entire reason gate and promotion logic gets pulled out of the manifest and into a script is so it *can* be given independent test coverage. A gate that decides promote-or-halt based on an error-rate threshold has real edge cases — a metric that lands exactly on the boundary, a data point that's missing or delayed, a metric that flaps across the threshold within the same evaluation window — and each of those is something a unit test pins down in milliseconds, with no controller, no cluster, and no live traffic required. A flag-targeting rule that resolves a conflicting override, or a generator that computes a canary weight from a step index, has the same shape: real branching logic that deserves the fastest feedback loop available rather than being deferred to whatever a live rollout happens to exercise.

## What counts as declarative: verify it, don't unit-test it

**The rollout manifest itself — the canary/blue-green steps, the traffic-shifting wiring, which gate is attached where — is not unit-testable in any meaningful sense, and trying to force it into that mold produces tests that mock the progressive-delivery controller rather than exercise it.** This half is proven by `verification`: run the rollout against a test environment and observe what it actually does.

The reason a unit test is the wrong tool here is the same reason it's wrong for IaC resource blocks and pipeline glue: the manifest has no interesting internal logic to isolate — its entire behavior *is* its integration with the controller, the metrics provider, the traffic-routing layer. A test that mocks the controller to make the manifest "testable" verifies only that the manifest calls the mock the way the test author expected — a tautology that would pass even if the real manifest pointed a gate at the wrong metric, wired a step to the wrong weight, or never actually attached the analysis template it was supposed to. What actually needs answering — "does the canary progress when the signal is healthy," "does a bad metric actually halt it," "does rollback actually revert" — can only be answered by running the real thing.

## Validate + entrypoint-smoke-invoke is the always-runnable minimum

**Two checks run offline, before any rollout is attempted, and there's no excuse for skipping either: validate/lint the rollout manifest against the controller's schema, and smoke-invoke each extracted script through the exact entrypoint the rollout calls — `./gate.sh --dry-run`, `python -m rollout.promote --help` — plus a tool-level dry-run where the controller supports one.**

A script's unit tests import its functions directly; the rollout invokes it through a CLI entrypoint or console command. Those are two different call paths, and unit tests exercise only the first. A wrong module path, a renamed script, a broken argument parser, a manifest that references a metric name the analysis template doesn't define — none of it shows up in a green unit suite, and all of it fails on the first real rollout, usually mid-canary where it's most expensive to discover. Validating the manifest catches the class of error that never depends on a live controller at all — a malformed field, a reference to a step or template that doesn't exist. Smoke-invoking each script through its real entrypoint proves the seam between the tested logic and the way the rollout actually calls it is connected — not a re-test of the logic itself, but confirmation that `rollout.promote` really is the module name and the CLI really does accept the flags the manifest passes it. Because both run without a live rollout, a test environment, or any traffic, they're the minimum verification that must happen even when nothing else can — the rollout equivalent of `validate` + `plan` for IaC, or entrypoint-smoke-invocation for pipeline scripts.

## Run the rollout in a test env and observe: progress, halt, and revert

**Once the manifest validates and every script's entrypoint resolves, verify the rollout for real: run it against a test environment and observe three concrete outcomes — the canary progresses when the health signal is genuinely healthy, a bad metric actually halts it, and a rollback actually reverts.** This is evidence, not inspection — reading the manifest and reasoning that the gate "should" catch a bad metric is exactly the failure mode verification exists to rule out, the same way reading application code without running its tests would be.

Concretely: trigger the rollout against an environment close enough to production's shape that the outcome is trustworthy, and capture what actually happened at each of the three points — the canary's traffic weight advancing through its steps on a healthy signal, the halt actually stopping progression when the metric crosses the threshold (prove it by making the metric bad and watching the halt happen, not by assuming the gate would catch it), and the rollback's outcome inspected afterward. A rollout whose gate has never been observed halting anything is a gate whose enforcement is still just an assumption, no matter how carefully the manifest was read.

## Prove the rollback path by actually exercising it

**A rollout is not verified — no matter how green the forward path looks — until its rollback has actually been triggered in a test environment and observed to revert. Reading the rollback section of the manifest, or watching only the forward canary succeed, proves nothing about whether the undo works.**

This is the deployment-specific case where "verify, don't inspect" carries the most weight, because the rollback path is exactly the code that only runs during an incident — the one moment where a plan that turns out to be wrong is most expensive. A forward path that has been run a hundred times says nothing about a rollback that has been run zero times: they exercise different code paths, different assumptions about what state the previous revision needs, different interactions with whatever migration or compatibility window is in play. Prove it the same way the halt gate gets proven — not by assuming it would work, but by actually triggering the rollback in the test environment and confirming the system lands back in the prior, known-good state. Per `rollout-authoring-hygiene.md`, this has to happen before the forward rollout is trusted with real traffic at all; here it's restated as a verification fact: a rollback that's only ever been read is unverified, full stop, regardless of how much passed on the way there.

## Shrinking the surface only verification can cover

**The amount of rollout automation that only manifest-reading and test-env runs can prove correct is not fixed — it's a direct consequence of how aggressively gate, promotion, and flag logic gets pushed out of the declarative config and into tested scripts per `rollout-authoring-hygiene.md`. The more of the actual decision-making lives in something `strict-tdd` can reach, the less of the rollout is doing anything beyond "wire this already-tested script into this step."**

A rollout where every threshold and every promotion condition is inlined directly into the manifest has almost nothing strict-tdd can reach — nearly all of it, including every edge case, has to be proven by running the whole thing end to end in a test environment, every time, for every change. A rollout where that logic has been extracted into tested scripts inverts the ratio: the edge cases are covered fast and locally by unit tests, and verification is left with a genuinely smaller job — confirming the wiring between already-trusted pieces converges the way the manifest says it will, and that the rollback still reverts — instead of standing in for all the testing the rollout logic never got.
